# standardized-cookies Specification

## Purpose
Standardizes the generation, attributes, and clearing of all authentication and session cookies across the service to eliminate configuration drift, prevent cross-site scripting (XSS) and cross-site request forgery (CSRF), and ensure proper behavior across both HTTPS and local development environments.

For architectural diagrams and component details, see [Architecture Design: Standardized Cookie Pipeline](../../design.md#standardized-cookie-architecture).

## ADDED Requirements

### Requirement: Centralized session cookie issuance
All session cookies (`session_id`) set by the service SHALL be constructed through `CookieManager`. Handcrafted `http.Cookie` definitions for session management in HTTP handlers SHALL NOT be permitted. The session cookie value SHALL be encrypted and authenticated using authenticated encryption (AEAD).

#### Scenario: Successful login sets standardized session cookie
- **WHEN** user authentication succeeds via either OIDC or OpenID
- **THEN** the system issues a `Set-Cookie` header for `session_id` configured with `HttpOnly: true`, `SameSite: Lax`, `Path: "/"`, and expiration aligned with the session lifetime
- **THEN** the cookie value is encrypted and tamper-proof

### Requirement: Dynamic secure flag evaluation
All cookies generated by the service SHALL have their `Secure` attribute evaluated dynamically based on the incoming request transport. If the request was made over TLS (`r.TLS != nil`) or arrived through a secure reverse proxy (`X-Forwarded-Proto: https`), the `Secure` flag SHALL be set to `true`. If the request was made over plain HTTP, the `Secure` flag SHALL be `false`.

#### Scenario: Request over HTTPS sets Secure flag
- **WHEN** an authentication or session cookie is generated for an HTTPS request or with `X-Forwarded-Proto: https`
- **THEN** the emitted `Set-Cookie` header contains `; Secure`

#### Scenario: Request over plain HTTP omits Secure flag
- **WHEN** an authentication or session cookie is generated for a plain HTTP request without secure forward headers
- **THEN** the emitted `Set-Cookie` header omits the `; Secure` flag, allowing local development and testing

### Requirement: Standardized cookie clearing on logout
When a user logs out, the system SHALL clear the session cookie through `CookieManager` using identical cookie attributes (`Path: "/"`, `HttpOnly: true`, `SameSite: Lax`, matching dynamic `Secure` setting) with an expiration timestamp in the past (`time.Unix(0, 0)`).

#### Scenario: Logout clears session cookie cleanly
- **WHEN** a client sends `POST /auth/logout` with an active session cookie
- **THEN** the session is removed from storage
- **THEN** the response includes a `Set-Cookie` header for `session_id` with empty value and an expired timestamp

### Requirement: Authentication state and nonce cookie cleanup
After processing an authentication callback (whether successful or failed), the system SHALL clear the `oauth_state` and `oauth_nonce` cookies via `CookieManager` with the standardized attributes (`Path: "/"`, `HttpOnly: true`, `SameSite: Lax`, matching dynamic `Secure` setting) and an expiration timestamp in the past (`time.Unix(0, 0)`).

#### Scenario: Successful authentication callback clears state and nonce cookies
- **WHEN** an authentication callback is processed successfully
- **THEN** the system clears the `oauth_state` and `oauth_nonce` cookies via `CookieManager` using standardized attributes and expired timestamps

#### Scenario: Failed authentication callback clears state and nonce cookies
- **WHEN** an authentication callback fails verification, receives an error, or encounters an invalid state
- **THEN** the system clears the `oauth_state` and `oauth_nonce` cookies via `CookieManager` using standardized attributes and expired timestamps before returning the error response
